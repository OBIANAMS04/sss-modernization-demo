Demo · Scene 9

Every change is timed

  • Each update is timed until the next request can read it.
  • Target: 30 seconds for 95% of updates, for each data type.
  • A real 31-second slowdown on profile saves raised the alert.
Scene 9, data freshness (STORY-009): every profile save, eligibility check, application and case change is timed from the start of the write until a separate read sees it, the way the next request would. Staff see each data type against a 30-second target for 95% of updates. To show the alert is real, the demo held one applicant's database row locked for 31 seconds while that applicant saved their profile: profile updates went over target and the page raised the alert, while every other data type stayed in the milliseconds. The slowest-updates list shows the time went into the write, not the wait to read. Check now times a write end to end from the browser. Measured on the demo deployment, which reads straight from its database; the same check will measure cache or replica lag once those exist.
