### What the demo does today
- Register/login (bcrypt passwords **and SSNs**, 1-hour JWT), demo-data banner, masked SSN entry.
- Profile (phone, address, income, hardship) with compliance check (18+, phone, address).
- Exemption eligibility: Type A senior (65+), Type B income (< $20,000), Type C hardship (Pending Review), each with a reason; audit-logged. These are illustrative rules, not Selective Service policy.
- Case management: apply → Submitted → In Review → Approved/Denied (reason required) → Appeal; timeline, in-app notifications, internal notes, document links, staff filters, CSV export (no SSNs).
- Compliance validation: every approval or denial is checked against 8 decision controls (eligibility basis, re-check after a profile change, denial reason and notice, separation of duties, assignment, review before decision, required document, audit entry). A failure opens a review that a *different* case manager resolves with a justification (accept the exception, recorded as an override, or reopen the case). Staff get a compliance dashboard (99% target with an alert) and a filterable audit log of every control result.
- Data freshness: every profile save, eligibility check, application, case status change and assignment is timed from the start of the write until a separate read sees the new row version. Staff get a Data Freshness page: p50/p95/p99 per data type against 30 s for 95% of updates, an alert when a type falls behind, the slowest updates (write time vs. wait time), and a Check now end-to-end test from the browser.
- Security audit log: every registration, sign-in (failed ones under the address tried, never the password), sign-out, MFA step, refusal (401/403), successful API read, export, profile change (field names only), decision, override, role grant or removal, deployment, configuration change between server starts (secrets named, never their values) and alert is recorded with who, when and the caller's address. The database refuses UPDATE, DELETE and TRUNCATE on the log (triggers, migration 015); each entry has a retain-until date 7 years on; SSNs, passwords, codes, tokens and secrets are removed before writing. Staff search it on a Security Audit Log page by date, user, event, area and result.
- Accessibility (Section 508): every page passes WCAG 2.1 AA checks for each role in an automated Chrome audit (axe-core rules, keyboard with a skip link and visible focus, titles and landmarks, nothing lost at 320 px, announced form errors); a warning two minutes before a session ends with Stay signed in (sessions end 12 hours after sign-in); 4.8:1 field borders; applications and appeals confirmed before they are sent.
- Citizen dashboard: each application with its status and the next step, eligibility with reasons and what the profile is missing, the 10 latest case events (applicant-visible only, one rule shared with the case page), notifications.
- Two-step verification at sign-in (STORY-003): a QR code and key set up an authenticator app (Google Authenticator, Authy, Microsoft Authenticator). After the password, the person gets a 5-minute pending token that every route refuses, then enters a 6-digit code (RFC 6238, one 30-second step either side; the same code never works twice; 5 tries per sign-in). Turning it off needs a code; the key is shown once; every step is audited without the key or code. Our own review found that a pending sign-in could be redeemed twice; it is now single use, decided in one statement, and an end-to-end check reproduces the gap and failed on the old code.
- Case manager dashboard (STORY-013, "My Work"): my open cases; waiting on me (cases to start, to decide, and compliance reviews of other managers' decisions); the unassigned queue; overdue cases (more than 5 days without an update); recent decisions; and a search that opens the case list already filtered (the filters are in the address).
- Admin dashboard (STORY-014): all cases by status and type (charts and tables), team performance (open, decided, median days to decide, compliance pass rate), and system health (database and migrations, deployed commit, freshness against 30 s, compliance against 99%, refusals in 24 hours, staff by role).
- Leadership dashboard (STORY-015): KPIs (total applications, approval rate, average processing time, open cases, appeal rate), 12-week trends, bottlenecks by stage (average days, cases stuck more than 5 days) and team performance. Aggregates only, no applicant data; leadership does no case work.
- Roles and Staff Access: citizen / case manager / leadership / administrator. Administrators give or remove case manager, leadership and administrator access in the app (Staff Access, `/staff`); case managers can only give case-manager access. Always with a reason; never your own, never the last case manager, never the last administrator; recorded in the same transaction as the change; the person is notified. `ADMIN_EMAILS` sets up the first administrator from existing case managers only; on 2026-10-14 the owner set it on Render and his case-manager account became the demo's administrator. `CASE_MANAGER_EMAILS` only sets up an empty system.
- Access policies (STORY-016): every API request is decided by Open Policy Agent before any route runs. The Rego policy has OPA's own tests and is compiled by OPA 1.21.0 to WebAssembly and evaluated inside the API. Rules use role, resource type, action and owner or assignee, including the story's example, "case managers can view and work cases assigned to them". Administrators change rules without a deploy on an Access Policies page (switch rules, narrow routes; a reason is required; versions are write-once; each change is audited as a policy change and applies at once). Refusals are audited with the rule and policy version. The policy can refuse what the code allows, never allow what the code refuses (the route guards stay). Sign-in, health and the policy pages are locked so administrators cannot be locked out. Our own review found that the earlier "API governance" service claimed to enforce OPA but never called it and was never wired in; it was removed.
- Policy assistant (STORY-017 to 020, 022 to 024; the plan and our acceptance criteria are in `docs/R2-MILESTONE-1-PLAN.md`): 8 synthetic policy documents (clearly labelled as not Selective Service policy) are split into 43 passages with a full-text index, re-indexed when a document changes, and each change is audited. Citizens and staff ask questions on an Ask about policy page; Claude answers only from the retrieved passages, with numbered citations that open the quoted policy text. SSN-shaped text is removed before anything is searched, stored or sent; 20 questions an hour per person and a daily cap on AI answers. Every answer is checked before anyone sees it: each statement needs a citation, and any number, date or amount must appear in a cited passage; a staff panel shows the failure rate for 7 and 30 days against a target below 2%. The assistant never decides eligibility: questions about a person's own case, answers that fail the check and answers people report go to an Assistant Reviews queue, where a case manager (never the person who asked) approves, corrects or declines with a note; the person is notified and sees the reviewed answer. The override rate (corrected answers, accepted compliance exceptions, and decisions against the automatic eligibility result) is on the admin and leadership dashboards with a 12-week trend against a target below 20%. The evaluation of 33 questions, run against Claude on the demo deployment on 2026-10-20, scored 100% on retrieval, key facts, citation validity and grounding (targets 90%, 85%, 100%, 98%); median answer 3.1 s.
- Drift detection (STORY-021): an AI Quality page for staff with nine daily quality signals from real answers (grounded rate, withheld, level 1, no answer, citations, length, p95 latency, negative feedback, reports), the last 7 days against the 28 before with a tolerance per signal and a 20-answer minimum, change markers when the model or the policy documents change, and server-side runs of the 33-question golden set that an administrator starts (at most once an hour, audited) and can mark as the baseline. Drift opens an alert: an audit event and a notification to administrators.
- Bias and fairness (STORY-025): 383 rule tests show names suggesting different genders and ethnicities, every US region, and phone and address formats never change eligibility or compliance outcomes; a counterfactual set of 10 questions in 7 forms (stated name, gender, ethnicity, age wording, disability, English fluency) must keep the same passages and oversight level in 95% of pairs and the key facts in every answer; approval rate, days to decide and override rate by age band and region, with the four-fifths rule. The demo collects no race, sex, ethnicity, religion, disability or national origin, and the page says why. Our review found that words people say about themselves changed which passages were found (52 of 60 pairs); the search now uses the asking sentence, falling back to the whole question when it has no searchable word (60 of 60, golden set 33 of 33).
- Observability (STORY-026 to 029): OpenTelemetry tracing of HTTP, Express, PostgreSQL and each Claude call (tokens, cost, latency, never the question); a trace id on every response, log line and audit entry; JSON logs, with expected refusals as warnings and only real faults as errors; per-route per-minute request, error and latency rollups kept 30 days, database time and pool use; tokens and estimated cost on every AI call. An Observability page for administrators, and service level objectives (availability 99.5%, p95 under 2 s, error rate under 1%, AI spend under the daily budget, drift and fairness) checked every minute over 1 and 24 hours, opening and closing alerts, each with a runbook entry. Export to Datadog or any OTLP backend is one setting (OTEL_EXPORTER_OTLP_ENDPOINT); without it nothing leaves the server.
- Load and performance (STORY-030 to 033): a pinned load harness (autocannon 8.0.0) with four journeys; on the local stack throughput about doubled and p95 at 16 connections halved after the fixes, and no request fails at any step up to 128 connections (before, 96 to 98% failed at 64 and 128). One light live run: 25 connections for 60 s, p95 1.24 s, 0 errors. The fixes: a full connection pool is "very busy" for that request, not a database outage; no connection held while hashing; a pool of 25; identical staff dashboards requested together share one computation; the role read once per request (never cached between requests); audit entries written in small batches; cheaper token checks; three indexes (migration 026). Production sizing for 10,000 concurrent users in `docs/PRODUCTION-SIZING.md`, every number labelled measured, derived or assumed.
- Database outage (STORY-034): the API keeps running without its database, answers 503 with Retry-After, and recovers by itself without a restart; a release that cannot migrate never replaces the running one. The multi-region production design is `docs/FAILOVER.md` (a design, not deployed).
- Uptime check (STORY-036): GitHub Actions checks the API and the site every 30 minutes from outside Render, opens an issue on failure and closes it on recovery.
- Security hardening (STORY-041; docs/SECURITY-TESTING.md): an attack suite of 52 checks (sign-in bypass and token tampering, other people's records, SQL and script injection, guessing, sign-out, recovery codes, headers and CORS). Sign-out ends the session on the server (every token of that sign-in, extended ones too); sign-in throttled per account and per address, registration per address (429 with Retry-After); response time no longer tells which addresses are registered; security headers on every API response and a content security policy on the site (the accessibility audit fails on any violation); bad request bodies are 400/413, not 500s; ten one-time MFA recovery codes (shown once, hashes kept); bcrypt 6, axios patched, unused uuid removed. Our own testing, not a third-party penetration test.
- Accessibility Conformance Report (STORY-042): VPAT 2.5, WCAG 2.1 A and AA and Revised Section 508, honest about the hands-on screen-reader test still owed and the two-step timeout without a warning.
- Operations documents (STORY-037 to 040): incident playbook with the October outage as a blameless review, operator runbook (deploy, roll back, rotate secrets, restore, security operations), administrator guide and user guide.
- Staff training (STORY-035): a Training page for case managers, administrators and leadership, with modules built from screens of the real pages and a knowledge check graded on the server (three of four right is a pass); attempts recorded (migration 028) and audited; administrators see the team's progress.
- Go-live readiness review (STORY-043 to 046; docs/READINESS-REVIEW.md): every story mapped to its evidence; drills on the live demo (rollback in 32 s and forward in 58 s; a Render export restored in 10.5 s with 0 errors and equal row counts); open gaps with owners; ten go/no-go criteria for a production launch.
- AWS GovCloud infrastructure as code (R0 STORY-004; infrastructure/aws-govcloud): VPC across three zones, ALB with WAF, ECS Fargate, Aurora PostgreSQL Global Database with RDS Proxy, KMS, Secrets Manager, CloudTrail, GuardDuty, Security Hub, Config, an Object Lock audit bucket; prod in us-gov-west-1 and a warm standby in us-gov-east-1; formatted, validated, TFLint clean; with an apply runbook and a cost estimate (about $5,850 a month, ±40%). Not applied.
- Data status (STORY-005): the citizen dashboard says how current the page is: when the person's records last changed and the measured freshness level (green under 10 s, yellow 10 to 20 s, red over 20 s), from `GET /api/data/pipeline-status`.
- The audit log records each visitor's own address (on Render, the address Cloudflare passes on); every deploy check confirms it.

## 4. Platform

| Layer | Choice |
|---|---|
| Frontend | React 18 + Vite + Tailwind v4 → Render static site `sss-demo-frontend` |
| Backend | Node + Express + TypeScript → Render web service `sss-demo-backend` (free tier, sleeps when idle); `ANTHROPIC_API_KEY` turns on AI answers (`AI_MODEL`, default `claude-opus-5-5`) |

| Source | https://github.com/OBIANAMS04/sss-modernization-demo (Render auto-deploys on push to master) |
| Access table | 71 routes, each with its access rule; a test fails the build if a route has none. Open Policy Agent (Rego policy compiled to WebAssembly, in the API) decides every request before any route runs and can only narrow what the code allows |
| Workflow | Claude commits and pushes each change; Render deploys; Claude verifies the demo deployment itself and posts the conclusion with screenshots to the BUILD ticket (one post per milestone, one composite image of several screens per post) |
| Verification | `scripts/verify-deploy.mjs`: served commits on every page path, database, migrations, and every protected route refuses requests without a token · `scripts/verify-live-citizen.mjs`: every staff route refuses a signed-in citizen · `scripts/evidence/<story>.mjs`: drives the UI in headless Chrome and captures the evidence pack in `docs/evidence/<story>/` · `scripts/evidence/composite.mjs`: the Basecamp image (refuses to leave out any evidence screen) · `scripts/e2e/policy.mjs`: the access policy end to end (23 checks) · `scripts/opa/build.mjs`: OPA's own tests, then the policy compiled to WebAssembly · `scripts/ai/eval.mjs`: the assistant's 33-question evaluation (retrieval, facts, citations, grounding) · `scripts/a11y/audit.mjs`: WCAG 2.1 AA, keyboard, reflow and session checks on every page (`--live` for the demo site) · `scripts/load/`: the load harness (`docs/evidence/r3-load/README.md`) · `scripts/e2e/failover.mjs`: the database-outage check · `scripts/e2e/security.mjs`: the attack suite (52 checks) · `.github/workflows/uptime.yml`: the uptime check every 30 minutes · plain `npx jest` runs every backend unit test |
